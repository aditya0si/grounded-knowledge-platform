# Results

Committed measurement output. Every file here is generated by a runner in
`src/gkp/eval/runners/` — none is hand-written, and no number is edited after the
fact. A new configuration produces a new file rather than overwriting an old one.

| File | Generated by | What it measures |
|---|---|---|
| `BASELINE.md` | `python -m gkp.eval.runners.baseline` | Dense retrieval alone, before hybrid or reranking |
| `ABLATION.md` | `python -m gkp.eval.runners.ablation` | *(M2)* the parameter grid, hybrid vs dense, rerank on/off |

Raw per-question rows are written to `results/raw/`, which is gitignored: they
are large, and the aggregate plus its confidence intervals is the artefact worth
versioning. The raw file for a run is named in that run's report, so any published
number can be traced back to the rows that produced it.

## How to read a number here

Every mean is printed with:

- **`n`** — how many questions it actually covers. A mean over 42 of 54 questions
  is not a mean over 54.
- **`excluded`** — rows whose metric was undefined. Unanswerable questions have no
  gold chunk, so retrieval cannot be scored for them; they are excluded rather
  than counted as zero, and the count is shown so the exclusion is visible.
- **A 95% percentile bootstrap interval**, seeded so that re-running an unchanged
  configuration reproduces the interval exactly. A mean over ~42 questions is not
  a point estimate, and printing one without an interval is a quiet lie.

## Reproducing

```bash
python scripts/tasks.py up            # Postgres + Redis + MinIO
python scripts/tasks.py eval-corpus   # rebuild corpus + golden set (writes corpus/, eval/golden/)
python scripts/tasks.py eval-retrieval
```

The report records the corpus hash, the golden-set hash, the embedder, the
chunking configuration, and the git commit, so a number is attributable to an
exact input. If any of those change, the number is a different measurement — and
the report says so rather than inviting the comparison.

### Cross-platform reproducibility, verified

The same evaluation was run on Windows 11 during development and on the Ubuntu CI
runner. Every metric, the corpus hash, the chunk count, and all 42 permission
controls matched exactly:

| | Windows 11 (local) | Ubuntu (CI) |
|---|---|---|
| corpus hash | `f8a20a1971ff9bd5` | `f8a20a1971ff9bd5` |
| chunks / questions | 325 / 54 | 325 / 54 |
| recall@10 | 0.9167 | 0.9167 |
| nDCG@10 | 0.7919 | 0.7919 |
| permission leaks | 0 | 0 |

This is what makes the CI gate possible at all: a gate on a number that drifts
between machines either flaps until it is loosened into uselessness, or fails on
every unrelated commit. Because the agreement is exact, the gate in
`.github/workflows/eval.yml` is set less than one question below the measured
baseline rather than at a comfortable margin.

## The one caveat that applies to everything here

**The corpus is synthetic.** The evaluation *methodology* is real and the corpus is
published and reproducible from a seed, but the document distribution is not a
real enterprise corpus. A system that scores well here has demonstrated that its
retrieval works on adversarially-structured internal documentation; it has not
demonstrated that it works on *your* documentation.
